# Bluetooth Logger — project memory

Android app: ground-truth log of Bluetooth connect/disconnect events, synced to Google Drive, used by a separate desktop reconciler to fix MileIQ's drive-classification mistakes. Companion to the Nestegg Rentals workflow over at `D:/Nestegg Google Drive/` — Richard runs the reconciler against MileIQ exports for HMRC mileage claims.

## Stack

- Kotlin 2.0, Android Gradle Plugin 8.7
- minSdk 31 (Android 12 — required for `BLUETOOTH_CONNECT`)
- targetSdk 35
- Jetpack Compose for the (single-screen) UI
- WorkManager for periodic Drive sync
- Google Sign-In + Drive REST API for upload auth
- JUnit 4 for JVM unit tests; no Robolectric / instrumentation tests yet
- Version catalog at `gradle/libs.versions.toml`

## Architecture

Receiver-only — no foreground service. Events arrive via push from Android.

```
ACL_CONNECTED/DISCONNECTED
  → BluetoothEventReceiver (manifest-registered, goAsync + single-thread executor)
  → EventStore (JSONL in app-private storage)
  → setup-health check + sync watchdog (force a fresh sync job when sync has stalled)

WorkManager (hourly, no constraints)
  → DriveSyncWorker (single-run lock: an overlapping run journals the skip and asks to be retried)
  → DriveClient → bluetooth-log-<deviceTag>-YYYY-MM.csv in Drive
```

Idempotency via per-month last-synced-byte-offset in `SharedPreferences`. Per-device CSV filenames so two phones on the same Google account never race on a single shared file.

## Source layout

`app/src/main/kotlin/com/nestegg/btlogger/`
- `BtLoggerApp.kt` — `Application`. Registers `AppForeground`, creates the setup-health notification channel and calls `SyncScheduler.ensureScheduled`.
- `AppForeground.kt` — `ActivityLifecycleCallbacks` counting started activities, read from any thread. `ActivityManager.getMyMemoryState` is **not** a substitute: a process running a manifest broadcast reports `IMPORTANCE_FOREGROUND` for the length of `onReceive`, which is exactly when the watchdog asks.
- `receiver/BluetoothEventReceiver.kt` — push-driven event capture; goAsync to a single-thread `BtLogger-disk` executor so the broadcast thread never blocks on disk. Also runs the setup-health check and `recoverStalledSync` on that same executor (the watchdog swallows its own failures, so the receiver does not wrap it). It is not the only watchdog trigger — `DriveSyncWorker` runs it too, because on the deep-sleep stall the broadcasts are exactly what stops arriving while the hourly worker still runs occasionally, and a receiver-only watchdog can then never post its alert.
- `setup/SetupStatus.kt` — pure issue decision (`bluetoothConnectGranted`/`batteryExempt` → `issues`/`isHealthy`); the only unit-tested piece of this feature.
- `setup/SetupChecks.kt` — `readSetupStatus(context)`: live-state reader (PowerManager battery-exemption + `BLUETOOTH_CONNECT` grant). Also exposes `isBluetoothAdapterEnabled(context)` for the heartbeat verdict and `isActiveNetworkValidated(context)` for the sync-attempt context. Infra, not unit-tested.
- `setup/SetupNotifier.kt` — channel creation plus **every notification this app posts, declared one way**: an `Alert` enum carrying the id, title and text of each (`SETUP_HEALTH` 1, `AUTH_NEEDED` 2, `SYNC_STALLED` 3, `SYNC_OFFLINE` 4), so nothing states a notification's identity in a second form. `update()` posts and cancels the setup-health one. The other three are the **sync-alert family** (`Alert.entries - SETUP_HEALTH`) and **exactly one of them can ever be standing**: posting any retires the rest, and `clearSyncAlerts` retires whichever is up. The auth prompt is inside that family deliberately — outside it, a stall alert reading *tap to open the app and sync manually* stacked on top of *tap to sign in again*, advising an action that cannot work against a token only the user can renew. The two verdict-driven entry points, `notifySyncAlert` and `retireSyncAlertsContradicting`, take the **`SyncHealth` verdict itself**, never an alert the caller derived: the verdict-to-alert mapping lives here, once, so no caller can pair a verdict with the wrong alert or dismiss the alert its own verdict wants showing. Suppressing an alert is not the same as clearing one — `retireSyncAlertsContradicting` posts nothing and leaves the alert the verdict still stands behind exactly as it is, which is what stops the tray and the banner stating opposite causes across the long silent arms (the grace window, and the whole time the app is open). Swapping one alert for another is a *new* notification rather than a rewrite, which is what makes the benign offline message escalating to the actionable stall message audible; re-posting the same one is silent. Every post is `setOnlyAlertOnce` — the channel is `IMPORTANCE_HIGH` and the setup-health check re-runs on the ACL path (four broadcasts per journey), so without it a re-`notify` of an unchanged warning heads-up and sounds each time — and every post is guarded by `areNotificationsEnabled()`.
- `storage/BtEvent.kt` — data class + hand-rolled JSON encode/decode (scalar helpers in `JsonLine.kt`).
- `storage/JsonLine.kt` — shared hand-rolled JSON scalar helpers (`appendJsonString`, `extractLong/Int/Boolean/String`) used by `BtEvent` and `SyncAttempt`.
- `storage/EventStore.kt` — JSONL append + tail-read with per-month byte offset; constructor accepts a `File` baseDir for JVM tests. Also exposes `lastRecordMillis`, `lastHeartbeat`, `recentConnections`.
- `sync/Heartbeat.kt` — pure domain: `shouldEmitHeartbeat` (24h-since-last-record) + `heartbeatStatus` (precondition verdict) over `CapturePreconditions` (`Measured`/`Unreadable`, so "the read threw" is a case rather than a null) and `DegradedReason`, which carries its own `wireName` the way `SyncTrigger`/`SyncOutcome` do. **`Measured` carries every device-state reading the verdict needs, and nothing else** — the `SetupStatus`’s `issues`, which is the only member the verdict reads, and the Bluetooth adapter flag, together — so the worker takes both under one `runCatching` and a throw out of *either* lands on `Unreadable`. That is why `state-unreadable` is the whole verdict when it appears rather than a token standing beside `bt-off`: a read that did not complete established nothing about the adapter either, and a token claiming otherwise would be fabricated. Unit-tested.
- `sync/SyncAttempt.kt` — pure domain: per-run record (`SyncTrigger` with `unattended`, `SyncOutcome` with `isClean`, timestamp/rows/error/context) + hand-rolled JSON encode/decode. Unit-tested.
- `sync/SyncJournalPolicy.kt` — pure domain: `SYNC_JOURNAL_CAP` + `retainWithinCap` (newest-N retention). Unit-tested.
- `sync/SyncHealth.kt` — pure domain: `SYNC_STALE_THRESHOLD` (6h), `SYNC_PERIOD` (1h, which `SyncScheduler` also builds the periodic request from) + an `isSyncStale` **nested inside its one caller**, the reportable verdict `syncHealth` (`HEALTHY` / `AUTH_EXPIRED` / `STALLED` / `OFFLINE`), and the watchdog decision `syncRecoveryAction` (`NONE` / `CLEAR_ALERT` / `ALERT` / `FORCE_REENQUEUE` / `FORCE_REENQUEUE_AND_ALERT`) with its forced-re-enqueue grace window, written as `SYNC_PERIOD.multipliedBy(3)` — **three hours** — so grace and period cannot drift into equality: a forced job restarts its interval at the force, so a grace of one period leaves it no headroom on the phone whose work the OS is already deferring. **The action says whether to force and whether to alert; *which* alert is `syncHealth`'s answer**, read straight off the verdict by `SetupNotifier`, so the notification and the in-app banner cannot say different things and no caller pairs a verdict with an alert by hand. Signed-out is one of its arms, not a caller-side gate: with no account there is nothing to recover and the stall alert's own instruction is unreachable, so it is cleared. It is carried by a **null `signedInSince`** rather than a separate `signedIn` flag, so neither this function nor `isSyncStale` can be handed a sign-in that does not exist. `SyncState.signedInSinceMillis` is null **whenever there is no account**; the converse does not hold, and the difference shows on one install — upgraded from a build that had no stamp, the account key is present and the stamp is not, so the getter reads `0L` and the domain treats the sign-in as the epoch, i.e. maximally stale until the first success lands (at most one hourly cycle, in which such an install can see the banner and one forced re-enqueue). **Staleness is measured from the later of the last success and the moment sync became possible** — the gate is inside the callee so no caller can forget it. The anchor is the sign-in, not the last *attempt*: anchoring on the attempt left a signed-in install whose periodic job JobScheduler never once dispatched permanently silent (`lastAttemptMillis` never leaves `0L`, so the watchdog scored `NONE` forever) — issue #4's own failure mode in the one variant the app could not see. The sign-in anchor keeps the fresh-install quiet that the attempt gate was added for (nothing is stale for the first 6h after signing in) and still fires when the worker never runs at all. The **grace window is a half-open interval anchored at the force** (`now >= lastForcedReenqueue && now < lastForcedReenqueue + 3h`), not an elapsed-time comparison: `lastForcedReenqueue` is stamped from wall clock, and a `Duration.between` that goes negative when the clock jumps backwards would read as “the force is still fresh” and silence the watchdog for the length of the jump — on exactly the stall it exists to surface. A stamp in the future is therefore no grace at all. **A standing auth failure is its own verdict.** With an expired Drive token the last recorded outcome is `auth-failure`, and once sync is stale the verdict is `AUTH_EXPIRED` rather than `STALLED`, because *tap to sync manually* cannot work against a token only the user can renew; both surfaces then say *sign in again*, and the one notification the family allows is the one that helps. **Connectivity chooses the message, never the force.** `syncRecoveryAction` takes the raw `NetworkStatus` and derives the verdict by calling `syncHealth` itself, so there is exactly one place in the codebase where connectivity is *interpreted* and both surfaces read its answer; the verdict is consulted for the alert alone, below every arm that decides whether to re-enqueue — an offline phone that has not synced in 6h is exactly the stall the watchdog exists for, and gating the force on a validated network would reinstate on the receiver path the very constraint the periodic backstop deliberately dropped (see the gotcha below). Both notify; neither is silent. For the same reason an `AppVisibility.FOREGROUND` sample suppresses the notification (never the force) when the sync-health banner is already on screen saying it. That an instantaneous sample stands in for a multi-hour history is a known and accepted limitation: the alert is only due after a force **and** an elapsed grace window with sync still stale, by which point a phone that had regained connectivity would have synced and cleared the condition. **`SyncRunContext` is the one other thing that holds a force back, and it is an impossibility rather than a policy**: the watchdog also runs at the end of every sync run, and `SyncScheduler.forceReenqueue` cancels the very periodic registration that run is executing under, throwing its `Result` away — the `Result.retry()` included. So from `INSIDE_SYNC_RUN` the decision never forces. It loses nothing: a run in progress is itself proof the job is being dispatched, which is the only thing a force repairs, so all that is left is to tell the user — and the alert is reached without waiting on a force that has nothing to fix. A force already pending still gets its grace window first, from inside a run exactly as from outside. Unit-tested.
- `sync/SyncJournal.kt` — bounded append-only JSONL journal of sync attempts (`File` baseDir for JVM tests); rotates via `retainWithinCap`, reads back with `retainedAttempts`.
- `sync/DriveClient.kt` — `appendCsvRows(yearMonth, deviceTag, header, rows)` (append) and `overwriteCsv(fileName, header, rows)` (wholesale replace, for the diagnostics snapshot); Drive `files.update` re-upload.
- `sync/DriveSyncWorker.kt` — iterates months, uploads new chunks, persists offset; reads the trigger from `inputData`; records a `SyncAttempt` on **every** return path, the overlapping-run skip included — a process-wide `Semaphore(1)` gates the run and the loser records the skip **without touching Drive**, then ends per `retryOrFail`. **Journalling a run is total**: `journalOnDevice` swallows and logs its own failure, because it is the recovery every failing path calls, and a recovery that can throw the very exception it is recovering from leaves the run in neither the journal nor the diagnostics CSV. It stamps `SyncState`'s last-attempt keys, which is what puts “Skipped, sync already running” on the screen of the user who just tapped Sync now and would otherwise be shown the previous run's outcome as if nothing had happened. Only `last_success` drives the watchdog and the banner, and a skip is not a clean outcome, so it cannot move either; the residue is that if the loser's preferences write lands *after* the winner's, the cosmetic “Last sync attempt” line reads the skip instead of the success it raced. **Drive is reached from exactly one scope, and that scope holds the permit**: `uploadDiagnostics` is declared inside `syncUnderPermit` and runs from its `finally`, so the diagnostics file is overwritten once per permit-holding run on every return path — the catch arm and the device-state abandonment included — and no path without the permit can reach it. The skip cannot race the permit holder's overwrite of that file, and that is now enforced by scope rather than remembered by a caller. `record` above it journals and clears the sync alerts on a clean outcome; it reaches no network at all. **Each step reports its own failure**: the heartbeat write carries its own `try` and abandons under its own name, the permit's catch labels a failed sync run, and `doWork`'s outer catch is the net for anything escaping either — it no longer describes every failure as a heartbeat failure, and the log line names the step, which is what `adb logcat -s DriveSyncWorker` is read for. **`retryOrFail` is the one place a run decides whether WorkManager should run it again**, and it turns on `SyncTrigger.unattended`: a periodic run retries, because `CANCEL_AND_REENQUEUE` cannot interrupt the blocking upload it cancelled and without a retry a forced recovery run is swallowed by the very run it replaced; a **manual** run never retries, because the user is standing there and the hourly run is the retry. Both the skip and the `IOException` path go through it. The capture-precondition read and the connectivity read are **separate** `runCatching`s, because they mean different things: a throw out of `PowerManager` leaves the capture preconditions unreadable, so the run journals an `error` row and abandons; a throw out of `ConnectivityManager` leaves only `network_validated` null and the run carries on, since connectivity is context on the row and not a capture precondition. Because they are `Boolean?`, that row reads as **unmeasured** rather than as a fabricated `false` the diagnostics reader would chase. Emits a liveness heartbeat before its early-outs — **every** one of them, the device-state abandonment and the overlapping-run skip included, because to the reconciler a missing heartbeat means the logger was dead — and its `DEGRADED:state-unreadable` verdict is raised by the device-state reads alone, never by the connectivity read, whose failure must not make the reconciler read a gap as unexplained. Mirrors the journal to `sync-diagnostics-<deviceTag>.csv` in Drive and raises the auth notification on `UserRecoverableAuth*`. Finally, on every path, it runs **`reportStalledSync`** — the watchdog entry point that alerts but never forces, because a force from here cancels the periodic registration this run belongs to (see `SyncHealth.kt`). The worker is still the watchdog trigger that fires when ACL broadcasts have stopped.
- `sync/SyncScheduler.kt` — the only place WorkManager is enqueued: `ensureScheduled` (**UPDATE**, not KEEP — see the gotcha below), `forceReenqueue` (CANCEL_AND_REENQUEUE — a genuinely new JobScheduler registration; it takes the `SyncState` and stamps the force itself, from its own clock read, so forcing without recording it is not a call anyone can make), `syncNow` (a one-time manual run under the unique name `drive-sync-manual`, enqueued **KEEP**, so a burst of taps collapses onto the one run already pending). `KEEP` **discards** the extra requests rather than queueing them, and the only pending state a tap may safely be discarded against is a manual run that is actually **running**. A manual `WorkSpec` left sitting `ENQUEUED` and never dispatched — this repo's own recorded failure mode, twice on this hardware — would otherwise swallow every later tap for the life of the install, the *Sync now* that the stall banner and the stall notification both offer as the escape from a stall included. So `syncNow` reads the unique work's state first and cancels anything unfinished that is **not** `RUNNING` before enqueuing; both calls go to WorkManager's serial task executor in order, so the cancel lands before the enqueue. The burst-collapsing property survives — a tap still leaves exactly one pending run — and a manual sync that is running is still never displaced, which is what `KEEP` was kept for. The periodic request carries **no constraints**, and its interval is `SYNC_PERIOD` from the domain, the same value the watchdog's grace window is a multiple of.
- `sync/SyncWatchdog.kt` — one private `readLiveSync(context)` assembles the live connectivity sample, the sign-in stamp, the last success, the last recorded outcome and the last force **once**, and carries the `SyncHealth` verdict computed from them, so the entry points above it cannot drift as the reading grows a field. `readSyncHealth(context)` is that verdict, the one the UI banner renders and the sync-side twin of `setup/SetupChecks.kt`'s `readSetupStatus`. Two entry points act on it, and **which one a caller may use is carried by the name rather than by an argument**: `recoverStalledSync(context)` — the ACL receiver and `MainActivity.onResume` — may force a fresh job registration; `reportStalledSync(context)` — the sync worker's own `finally` — may not, because the force would cancel the registration that run belongs to. Both **swallow their own failures**, so no caller has to remember to wrap the watchdog in a `runCatching`, and none does. Beyond handing `SetupNotifier` the verdict and letting it work out which alert that is, the `when` is exhaustive over `SyncRecoveryAction` and holds no condition of its own — every branch it takes was decided in the unit-tested domain function. **On every arm that does not alert it also retires the alert the verdict contradicts** — an offline alert standing while the phone is back online and still failing, and the reverse — because the arms that suppress an alert are the long-lived ones (the grace window, and the whole time the app is open), and without this the tray and the banner could state opposite causes for hours. Suppressing an alert is not the same as clearing one, so the alert that *matches* the verdict is left standing.
- `sync/SyncState.kt` — `SharedPreferences` wrapper (account name, per-account per-month offsets, last-attempt millis+outcome, last-success millis via `recordAttempt`, last forced re-enqueue via `recordForcedReenqueue`, whose only caller is `SyncScheduler.forceReenqueue`). **The two writers that stamp a time read the clock themselves** — `recordSignIn(accountName)` and `recordForcedReenqueue()` take no `nowMillis`, so no caller can hand one the wrong clock or forget to hand it one at all. The account is written only through `recordSignIn`/`recordSignOut`, never a settable property, because the sign-in timestamp is what staleness is measured from and setting one without the other would silently disarm the watchdog. **`recordSignIn` is a no-op when the account already recorded is the one signing in**: the stamp answers "when did sync become possible", which re-picking the same account in the Google chooser does not change, and because staleness is measured from the later of it and the last success, re-anchoring it would hide a real stall for a further six hours — reachable from the stall banner's own screen, via the *Switch Google account* button, on a path that enqueues no sync at all. **A byte offset is keyed by the account that earned it** (`offset_<yearMonth>|<account>`), and the only way to reach one is `signedInAccount`, which hands back a `SyncAccount` carrying the name it just read — no caller supplies an account name to an offset call, so an offset cannot be keyed against a CSV that account never wrote. A second account starts from zero against its own Drive files, and switching back resumes where the first left off. Wiping the offsets on a switch instead — the shape this started as — makes an A → B → A switch-back re-append the whole local month onto the CSV A already holds, which is the duplication the whole issue is about. `migrateLegacyOffsets`, declared inside the `init` block that is its only caller, re-keys the pre-account-keyed `offset_YYYY-MM` entries onto whoever is signed in the **first time this build reads the prefs** (which is the account that earned them: a sign-out cannot precede the new build's first run) and **drops** them when nobody is — never carrying them forward for a later sign-in to adopt, which would hand account A's offset to account B and silently skip B's month. Its key strings are hardcoded, not shared with the live format (`DATA-01`).
- `sync/CsvFormat.kt` — ISO-8601 UTC + RFC 4180 row formatter; event rows plus `diagnosticsRow`/`diagnosticsFileName` for the sync-diagnostics CSV.
- `sync/DeviceTag.kt` — stable per-device suffix (`<sanitised-model>-<8-char-android-id>`).
- `ui/MainActivity.kt` — single screen: sign-in, permission grant, manual sync (tagged `manual`, via `SyncScheduler.syncNow`), sign out (which also clears any standing stall notification), recent connect/disconnect list (last 10, heartbeats excluded), "Last alive check" line, "Last sync attempt" line (time + outcome, the overlapping-run skip included); setup-health banner and sync-health banner (no successful sync in >6h; the banner is declared inside `StatusScreen`, its only caller, and reads the verdict and callback off that scope rather than taking them as parameters; it renders `readSyncHealth`'s verdict and decides nothing itself — `STALLED` says syncing has stopped and offers *Sync now*, `OFFLINE` says the phone is waiting for a connection and offers no button, and `AUTH_EXPIRED` says the Drive sign-in has expired and offers *Sign in again*, each matching what the notification for the same verdict says). **`onResume` runs `recoverStalledSync`** — the stall notification opens this activity, and a dead periodic registration is repaired by `SyncScheduler.forceReenqueue`, which "Sync now" (a one-off `DriveSyncWorker`) cannot do. Without it, recovery from the app depended on an ACL broadcast arriving — the very signal that stops arriving in the deep-sleep stall.

## Known gotchas worth remembering

- **Implicit broadcast restrictions (Android 8+)** don't apply to ACL events for *paired* devices — they remain exempt. Manifest registration is the right call.
- **`BLUETOOTH_CONNECT` is required to receive ACL broadcasts at all** on Android 12+, not just to read names. Without it the receiver never fires; logcat is silent. Verified on the S20.
- **Reboot:** receiver re-registers automatically from manifest. Connections that happened during the reboot window are lost — accept this.
- **Toggling the BT adapter off/on does NOT fire per-device ACL events** on Samsung One UI (Galaxy S20 Android 13). Only `ACTION_STATE_CHANGED` for the adapter. The reconciler can't infer connect/disconnect from adapter state. Real ACL events fire only on actual link transitions (device entering/leaving range, pairing, explicit per-device disconnect from settings, BT device power-cycle).
- **Each connect/disconnect produces *two* ACL events for paired devices** — one on the BR/EDR transport and one on LE — within ~10s of each other. Reconciler must dedupe consecutive same-state events from the same MAC inside a small window.
- **`BluetoothDevice.getName()` requires `BLUETOOTH_CONNECT`.** Without it, `name` returns null. Receiver wraps in `runCatching` so we still log MAC.
- **Multiple simultaneous devices** (headphones + car): log all; reconciler picks the one matching a known-vehicle MAC.
- **Drive REST has no real append.** We re-upload the whole file via `files.update`. For monthly CSVs the size stays small (<200 KB).
- **Per-device CSV filenames matter** — `drive.file` scope means two phones on the same Google account otherwise race on a single shared file. Filename includes `<sanitised-model>-<8-char-android-id>` (see `DeviceTag.kt`). Reconciler should glob `bluetooth-log-*-YYYY-MM.csv`.
- **Samsung battery saver kills the app** unless the user explicitly excludes it (Settings → Apps → Battery → Unrestricted, AND Battery → Background usage limits → Never sleeping apps). Without this, expect gaps. README documents the steps. The app now self-warns (banner + worker notification) when it loses the **Doze exemption**, but it cannot detect Samsung's separate *Never sleeping apps* list (no public API) — that step is still manual. Confirmed failure mode (Jun 2026, `sm-g981b`): an idle non-exempt app deep-sleeps, Android stops delivering ACL broadcasts (the BT *stack* still connects — visible in `dumpsys bluetooth_manager` A2DP StateMachine history), yet the hourly WorkManager sync still runs occasionally, so the CSV freezes with no visible symptom. `BLUETOOTH_CONNECT` stays granted throughout — don't assume permission loss.
- **Liveness heartbeat** — during ≥24h of Bluetooth silence the hourly worker appends a `HEARTBEAT` row (`event_type=HEARTBEAT`, verdict in `device_name`, empty MAC) so the reconciler can tell genuine no-car-use from a logger fault. It proves the logger was *alive* and capture *preconditions* were green (`OK`) or not (e.g. `DEGRADED:perm-missing+no-doze-exemption+bt-off`, failing tokens joined by `+`; `state-unreadable` means the run could not read the preconditions at all, not that they were bad) — **never that capture succeeded** (the deep-sleep case decouples WorkManager from ACL delivery). The reconciler must exclude `HEARTBEAT` rows from drive-matching/dedup; **heartbeat absent across a gap = total death, gap untrustworthy.**
- **Sync-diagnostics CSV** — alongside the event CSVs the worker uploads `sync-diagnostics-<deviceTag>.csv` (columns: `utc_iso,trigger,outcome,rows_uploaded,error_class,battery_exempt,network_validated`), a **wholesale-overwritten** snapshot of the on-device journal's newest `SYNC_JOURNAL_CAP` (200) attempts. It is *not* append-mode — each sync replaces the whole file — so the reconciler reads the current window, not an ever-growing tail. Use it to distinguish "worker never ran" (no recent rows) from "ran but upload failed" (rows with `auth-failure`/`io-retry`/`error` outcomes) after a stall. **`battery_exempt` / `network_validated` can be empty**, which means the run died before those readings were taken — read a blank as *unknown*, never as `false`. A false `battery_exempt` is the headline signal for the Samsung deep-sleep failure mode, so a fabricated one would send the reader chasing a Doze exemption that is fine.
- **JobScheduler can stop dispatching the periodic sync for weeks, with nothing wrong anywhere.** Twice now (Jul 2026, and 12 Aug – 1 Sep 2026 for 484h). App Standby Bucket `EXEMPTED`, Doze whitelisted, never force-stopped, WorkSpec `ENQUEUED` with a live JobScheduler job — the job simply was not run, and `ExistingPeriodicWorkPolicy.KEEP` is blind to present-but-not-dispatching, so the hundreds of `Application.onCreate` calls during the stall re-enqueued nothing. **`ensureScheduled` therefore uses `UPDATE`, never `KEEP`** — under `KEEP` an already-installed phone keeps the `WorkSpec` it registered on first launch, constraints and all, so any change to the request (the dropped network constraint most of all) would reach only a fresh install. `UPDATE` rewrites the spec in place and preserves `lastEnqueueTime`, so the hourly cadence is not restarted by process churn; `CANCEL_AND_REENQUEUE` would restart it and is reserved for the watchdog. **We do not root-cause this; we mitigate and detect.** The watchdog runs on each ACL event, on every resume, and at the end of every sync run: if no sync has succeeded in ≥6h it calls `SyncScheduler.forceReenqueue` (CANCEL_AND_REENQUEUE), waits out a three-period (3h) grace window, and if still stale forces again and posts a stall notification (unless an activity is started, where the banner already says it). The worker runs the same watchdog at the end of every run, because in the stall the receiver is what goes quiet. **`CANCEL_AND_REENQUEUE` does not stop the run it cancels** — coroutine cancellation is cooperative and `runSync` is blocking throughout, so the cancelled run keeps the single-run permit until its upload finishes and the replacement would otherwise skip and be dropped; the skip path of an unattended run returns `Result.retry()` precisely so the forced run survives that window. Capture kept working perfectly throughout both stalls — one delivery mechanism dead, another perfect, same process.
- **The periodic sync request deliberately carries no constraints.** `NetworkType.CONNECTED` compiles to a `NetworkRequest` demanding `NET_CAPABILITY_VALIDATED`, and it was the only constraint the never-dispatching periodic job had that the always-works manual request lacked. Offline runs now surface as `io-retry` journal rows — the periodic one retries with backoff, a manual one just records and stops — which is cheaper than a constraint we cannot observe being evaluated. Do not add it back.
- **OAuth "Testing" mode blocks anyone not on the test-users list** — including the developer's own account. Symptom: "access blocked, app has not completed verification". Add the account in the OAuth consent screen → Test users.
- **`statusCode=10` (`DEVELOPER_ERROR`) at sign-in** = the OAuth Android client in Cloud Console is missing or its SHA-1 doesn't match the signing keystore.

## Conventions

- Source under `app/src/main/kotlin/` (not `java/`) — explicit `srcDirs` in `app/build.gradle.kts`. Same for `src/test/kotlin/`.
- Package: `com.nestegg.btlogger`.
- App namespace: `com.nestegg.btlogger`. Application id: same.
- Don't add a foreground service — defeats the "lightweight, push-only" design unless we hit a real reliability issue.
- Don't introduce JSON or CSV libraries — the schemas are tiny and well-known; hand-rolled keeps deps minimal.

## Testing tiers — and the one deliberately missing

`:app:testDebugUnitTest` (JVM, JUnit 4) covers the pure domain, and `.github/workflows/build-test.yml`
runs it plus `:app:assembleDebug` on `main` and on PRs targeting it. **There is no automated
on-device or instrumentation tier** — no `androidTest` source set, no Robolectric, no emulator in CI.

**That is a deliberate choice, not an oversight**, and it knowingly diverges from the parent repo's
`TST-03`. Every failure this app actually suffers lives where an emulator cannot see: JobScheduler
non-dispatch, Doze, Samsung's *Never sleeping apps* list, real ACL delivery, and the Drive OAuth
round-trip (which needs credentials CI does not hold). A green emulator run would prove nothing
about the two phones, and #4's sync lock has no reachable test seam at all.

**What is verified by hand instead** — the checklist run on `sm-g981b` / `sm-g981u1`. These runs
leave no written artifact: nothing in the repo, and nothing on the PR, attests that any given run
happened, so read the list as the procedure, not as evidence it was followed.
- `./gradlew :app:installDebug`, then drive sign-in, permission grant, Sync now, and a real
  connect/disconnect.
- `adb logcat -s BtEventReceiver BtLoggerUi DriveSyncWorker SyncWatchdog`.
- `adb shell dumpsys jobscheduler | grep -A40 com.nestegg.btlogger` — job id, generation, and the
  required-constraints list (which must show no `CONNECTIVITY`).
- The Drive files themselves: `bluetooth-log-*-YYYY-MM.csv` and `sync-diagnostics-*.csv`.

**Closing the gap would mean**: an `androidTest` source set, `androidx.work:work-testing` (its
`TestDriver` can force periodic work to run), Compose UI test artifacts, a dedicated Drive test
account with its own OAuth client, and an emulator step in `build-test.yml` — for coverage that
still stops short of Doze, OEM battery policy and real ACL delivery. Tracked as **issue #6**, which
needs a grilling session before it is codeable.
